# Worktrace 실사용 요구사항 재정의

기준일: 2026-09-14. 분석 기준 커밋: `87bb97a`.
상태: 구현을 위한 제안 명세. 이 문서의 목표 동작을 구현 완료로 해석하지 않는다.
현재 구현은 README와 DESIGN.md, 이번 이후 제품 우선순위는 이 문서에서 구분하여 관리한다.
운영 DB, GitHub 계정 권한, 실제 배포 버전은 이번 분석에서 확인하지 않았다.

## 1. 서비스 정의

**Worktrace는 GitHub 활동과 직접 기록한 업무를 근거로, 실제 계획·수행·문제 해결·개인 기여를 관리하고 검토 가능한 경력 자료로 전환하는 개인 업무 기록 서비스다.**

핵심 흐름은 `수집된 근거 -> 업무 연결 또는 후보 검토 -> 수행 이력 -> 확인한 성과 -> 경력 자료`다.
GitHub를 다시 그리는 서비스, 커밋 수를 진척으로 바꾸는 서비스, AI 문장만 생성하는 서비스를 목표로 하지 않는다.
사용자는 이미 알고 있는 정보는 다시 입력하지 않고, 시스템이 알 수 없는 목적·기여·결과만 보완한다.

### 사용자와 범위

- 1차 대상은 본인의 프로젝트를 관리하는 단일 사용자다. 조직·과금·다중 사용자 권한 확장은 제외한다.
- 최초 관리 대상은 `Leegiyeon/oncc`, `RotemSRS/emanual`, `Leegiyeon/worktrace`다. 실제 연결은 이름 대신 GitHub repository ID로 확인한다.
- `emanual`은 사용자 진술상 개발 종료·서비스 운영 중이다. 이 진술과 운영 DB 반영 여부를 구분한다. 실제 종료일·개인 기여·성과 수치는 미확인 상태로 둔다.
- 다른 프로젝트의 진행 단계와 운영 상태는 이름이나 최근 커밋만으로 추측하지 않는다.
- 1차 입력은 기준 브랜치(main 기본)의 push, Issue·PR 정보, 직접 작성한 업무 기록이다. GitHub에 없는 회의·설계·협업·장애 대응도 관리 대상이다.
- 문서 업로드/OCR/RAG, 공개 포트폴리오 호스팅, GitHub 쓰기 동기화, 브랜치 자동 병합·삭제는 이번 필수 범위가 아니다.

소유권 용어를 구분한다. `owner_id`는 Worktrace 데이터 소유 사용자이며 GitHub 저장소의 개인/조직 소유자, Git 작성자, 성과 기여자는 서로 다르다. 권한이 있는 조직 저장소 `RotemSRS/emanual`도 본인의 Worktrace 프로젝트에 연결할 수 있다. 조직 소유라는 이유로 근거를 거부하거나 개인 기여로 자동 인정하지 않는다.

## 3. 반드시 분리할 데이터

| 개념 | 의미와 소유권 | 자동 처리의 한계 |
| --- | --- | --- |
| 원본 근거 | repository ID, SHA, Issue/PR ID, 원문 URL, 작성자, 발생 시각, 수집 시각 | 수집 성공은 업무 완료·배포 성공·개인 기여를 의미하지 않는다. |
| 외부 상태 | GitHub의 Issue 상태·종료 사유, PR 상태·병합 여부 | 닫힌 PR과 병합된 PR, 취소된 Issue와 해결된 Issue를 구분한다. |
| 업무 후보 | 분류 규칙·AI가 제안한 작업 또는 기존 업무 연결 | 승인 전에는 계획 분모·완료 실적·확정 성과에 포함하지 않는다. |
| 계획 업무 | 사용자가 관리 대상으로 채택한 WBS, 완료 기준, 기한, 범위 | 외부 수집이 사용자 계획과 설명을 덮어쓰지 않는다. |
| 수행 이력 | 실제 작업·결정·장애·해결 과정과 연결 근거 | 커밋마다 사람의 서술형 업무 로그를 확정 생성하지 않는다. |
| 완료 확인 | 사용자가 기준·근거·남은 일을 확인한 기록 | AI는 선택적 보조다. 확인 주체·시각·당시 기준을 남긴다. |
| 성과 | 확인된 변화와 본인의 기여. 정량이면 측정 조건까지 포함 | 기록량·커밋 수·추측 시간을 성과 수치로 변환하지 않는다. |
| 경력 자료 | 선택한 프로젝트·기간·기여·확정 성과에 근거한 검토용 문안 | 원본 데이터나 성과 확정을 역으로 수정하지 않는다. |

출처와 확정 여부는 서로 다른 축이다. 사용자가 채택한 자동 후보는 출처를 지우지 않고 승인 이력을 추가한다.
기존 `source_provider`를 manual로 바꿔 신뢰한 데이터처럼 만드는 방식은 금지한다.
확정은 사람의 검토를 뜻하며 객관적 진실을 보증하는 인증 점수가 아니다.

## 4. 핵심 사용 시나리오

### S1. 진행 중인 프로젝트 등록

저장소 연결 -> 수집 범위 확인 -> 프로젝트 목적·본인 역할 입력 -> 기존 Issue/계획 가져오기 -> 관리할 업무만 채택한다.
수집 직후에는 기록만 보여도 정상이다. 계획이 없으면 `계획 미등록`으로 표시하며 임의 진척률을 만들지 않는다.

### S2. 매일 하는 일

main push 또는 Issue/PR 변경 -> 근거 수집 -> 기존 업무 자동 연결 또는 연결 후보 -> 대시보드에서 처리할 일 확인.
사용자는 분류가 맞으면 일괄 채택하고, 필요한 경우 수행 내용·결정·장애 해결을 보충한다.
커밋 내용이 충분한 정보는 다시 타이핑하지 않는다. 무관한 변경은 무시하되 근거는 보존한다.

### S3. 업무와 마일스톤 완료

완료 기준과 연결 근거 확인 -> 미완료 업무 해결 또는 범위 변경 이유 기록 -> 사용자가 완료한다.
AI 미설정·타임아웃이어도 같은 기준으로 수동 완료가 가능해야 한다.
작업 완료, 마일스톤 인수 확인, 프로젝트 개발 종료, 서비스 운영 중은 별개의 상태다.

### S4. 끝난 프로젝트 정리: emanual

개발 종료·운영 중 표시 -> 실제 이력 수집 -> 본인이 수행한 범위와 결과 정리 -> 근거 연결 -> 경력 자료 작성.
과거 계획이 없으면 회고용 수행 항목으로 정리하며 과거 진척률을 역산하지 않는다.
자동 생성된 미완료 WBS는 실제 잔여 업무인지 검토한 뒤 유지·범위 제외·다음 작업으로 이관한다. 일괄 100% 처리하지 않는다.
운영 중 표시는 사용자 확인 상태다. 별도 상태 수집 없이 실제 uptime이나 SLA로 표현하지 않는다.

### S5. 월간 정리와 이력서 작성

프로젝트 여러 개와 기간 선택 -> 개인 기여·확정 성과 선택 -> AI 요약 -> 문장별 근거 확인·수정 -> 검토한 버전 저장·Markdown 내보내기.
원본이 바뀌면 기존 문안을 조용히 덮어쓰지 않고 이전 기준의 자료임을 표시한다.
근거가 부족한 성과는 질문/보완 항목으로 남기며 숫자를 만들어 문장을 완성하지 않는다.

## 5. 필수 기능과 수용 기준

P0는 데이터 훼손·허위 현황·운영 위험을 막는 선행 조건이다. P1도 1차 실사용 완료에 포함한다.
P2는 그 이후 확장이다. 아래 요구사항은 신규 구현 목표이며 현재 충족 여부는 단계별 검증으로 판정한다.

### R01. 프로젝트 상태와 최초 실데이터 확인 [P0]

- 개발 단계와 서비스 상태(미확인/미출시/운영 중/종료)를 별도로 표현한다. 서비스 상태 자동 모니터링은 추가하지 않는다.
- 개발 종료 시 종료 근거·확인 시각·미완료 항목 처리 사유를 기록한다. 실제 종료일을 모르면 null로 유지한다.
- 상태는 인증된 데이터 소유 사용자가 확인한다. 본인 진술과 사유를 최소 근거로 허용하고 배포/인수 자료는 선택적으로 연결한다. 미확인 날짜를 현재 날짜로 대체하지 않는다. 개발 재개나 서비스 종료도 명시적 변경과 사유·이력을 남기며 GitHub 수집은 이 상태를 변경하지 않는다.
- 저장소 연결 전 repository ID와 소유자를 확인한다. 1차는 프로젝트당 대표 저장소 한 개를 지원하고 암묵적 재연결은 막는다.
- **수용:** emanual 개발 종료 후 수집·재수집·앱 재시작을 해도 종료 상태가 유지된다. 미완료 WBS를 done으로 바꾸지 않는다. 세 저장소가 서로 다른 프로젝트에 정확히 연결된다.

### R02. 복구 가능한 수집과 동기화

**R02a [P0]: 최초 이력·기준 브랜치 push·수동 재대조.** 아래 보존·실패 규칙은 이 세 경로부터 적용한다.

- main 기본의 설정된 기준 브랜치 push를 수집한다. 최초 가져오기와 수동 재동기화는 커밋 및 Issue/PR의 외부 상태를 읽는다.
- 최초 가져오기의 선택 기간과 실제 수집 범위를 남긴다. 전체 이력을 선택하면 페이지 종료까지 수집하며, 제한·중단 시 부분 수집으로 표시하고 재개한다.
- 전달 ID와 repository ID+SHA/외부 ID를 기준으로 중복을 막고, 오래된 이벤트가 최신 외부 상태를 되돌리지 않게 한다.
- GitHub 상태는 외부 원본, Worktrace 계획·메모·기여 확인은 사용자 소유다. 1차에는 GitHub로 쓰지 않는다.
- Issue 종료·PR 병합은 업무 완료의 근거/후보이지 로컬 완료 확인이 아니다. 기본 정책은 사용자 확인 전 승인 계획의 상태를 바꾸지 않는 것이다.
- 처리 완료 시각·실패 사유·조회 범위·누락 가능성·재시도를 표시한다. 실제 DB 반영 전 성공으로 표시하지 않는다.
- **수용:** 동일 전달 3회, 다른 전달 ID의 동일 SHA, 실패 후 재처리에도 근거와 업무 연결이 중복되지 않는다. 수동 메모·승인 상태가 보존된다. 역순 이벤트·재개된 Issue·병합 없이 닫힌 PR을 정확히 구분한다.
- **수용:** 수집 실패·토큰 만료·부분 페이지 조회는 성공 0건과 구분된다. 재대조가 성공하면 누락을 보충하고 마지막 성공 시각을 갱신한다.

**R02b [P1]: 일상 운영 자동화.** Issue/PR 변경 이벤트와 일일 정기 대조를 같은 수집 경로에 연결한다. 실시간 화면 스트리밍·분산 큐 구축은 필수가 아니다.

- **수용:** push 없이 바뀐 Issue/PR이 이벤트 또는 다음 정기 대조로 반영된다. 이벤트 누락 후 정기 대조로 복구되며 작업 중복 실행을 막는다. 마지막 대조와 실패·다음 재시도를 확인할 수 있다.

### R03. 원본·후보·승인 계획의 경계 [P0]

- 자동 분류는 우선 기존 업무와 연결하고, 연결이 불확실할 때만 후보로 제시한다. 같은 근거로 후보를 계속 만들지 않는다.
- 후보에는 출처·제안 이유·생성 방식이 있으며 채택·수정 후 채택·무시가 가능하다. 무시한 후보를 동일 버전 재수집으로 되살리지 않는다.
- 사용자가 채택한 업무는 출처와 채택 기록을 보존한다. 분류 규칙 수정이나 새 Issue 수집으로 삭제하지 않는다.
- **수용:** 커밋만 100건 수집한 프로젝트는 승인 계획이 없으면 완료율이 없다. 후보 채택 1회는 계획에 정확히 한 번 반영된다. 이후 동기화가 채택·무시 결과를 덮어쓰지 않는다.

### R04. 일관된 WBS와 완료 확인 [P0]

- 기본 완료율은 승인된 산정 대상 WBS의 완료 비율이다. 마일스톤 가중 방식은 사용자가 선택한 프로젝트 정책으로 명시한다.
- WBS 생성·편집·상태 변경·완료 검토·동기화 경로에서 같은 서버 측 규칙을 적용한다.
- 마일스톤 확인 기록은 합성 WBS 한 행의 존재에 의존하지 않는다. 확인은 기준·근거·사용자·시각·당시 데이터 버전을 갖는다.
- AI 결과는 수동 확인의 필수 조건이 아니다. 변경된 근거의 재확인이 필요하면 이유를 표시하고 이전 확인 이력을 보존한다.
- **수용:** 수동으로 만든 프로젝트와 마일스톤도 AI 키 없이 완료 확인할 수 있다. 기준이 없거나 남은 필수 업무가 있으면 서버가 차단하며, 범위 제외에는 이유가 필요하다. 일반 WBS API로 확인 조건을 우회할 수 없다.
- **수용:** 같은 데이터·같은 조회 조건은 대시보드, 상세, 리포트에서 같은 분모·분자·완료율을 반환한다. 프로젝트 종료나 PR 병합만으로 WBS 100%가 되지 않는다.

### R05. 업무·문제·이력 연결 [P1]

- 기존 WBS를 중심으로 커밋·PR·Issue·업무 로그를 연결한다. 동일 업무를 화면마다 복사 생성하지 않는다.
- 외부 GitHub Issue, 내부 문제/블로커, 높은 우선순위, 단순 기한 초과를 구분한다. 필터와 목록은 같은 원본을 조회한다.
- 실제 발생일, 완료 전이 시각, 수정 시각, 수집 시각을 분리한다. 상태 변경은 이전/이후 값·주체·사유를 기록한다.
- **수용:** 업무 하나에 커밋 여러 개와 로그를 연결하고 화면 간 이동해도 같은 ID와 상태를 본다. 완료 업무 제목만 고쳐도 이번 주 완료 실적에 새로 들어가지 않는다. 재개 후 재완료 이력을 구분한다.
- **수용:** GitHub에 기록하지 않은 회의·설계·장애 해결도 프로젝트에 기록하고 성과 근거로 연결할 수 있다.

### R06. 개인 기여와 확인한 성과 [P1]

- 프로젝트 전체 결과와 본인의 역할·수행·협업 기여를 분리한다. Git 작성자 일치는 후보 분류에만 쓰고 단독 기여로 확정하지 않는다.
- 성과에는 문제/이전 상태, 본인의 행동, 결과, 근거, 확정 여부를 둔다. 수치에는 단위·측정 기간·기준값·결과값·측정 출처를 함께 저장한다.
- 정량 근거가 없으면 정성 성과로 남긴다. 근거 URL 하나가 존재한다고 수치가 증명된 것으로 간주하지 않는다.
- **수용:** 팀원의 커밋이 본인의 이력서 실적으로 자동 들어가지 않는다. 사용자는 공동 기여를 명시할 수 있다. 근거 없는 수치는 확정할 수 없고 정성 초안은 저장 가능하다.
- **수용:** 다른 프로젝트 또는 다른 Worktrace 데이터 소유 사용자(`owner_id`)의 근거 연결을 API가 거부한다. 연결 근거 삭제·변경 시 확정 성과의 재검토 필요 여부를 표시하고 고아 참조를 숨기지 않는다.

### R07. 검토·재현 가능한 경력 자료 [P1]

- 프로젝트별 생성과 여러 프로젝트를 선택한 통합 경력 자료를 지원한다. 목표 역할·기간·포함 자료를 사용자가 지정한다.
- 기간은 수행/성과의 실제 발생 기간 기준이며 수정일 기준이 아니다. 기간 미확인 자료는 기본 제외하고 별도 표시한다. 포함을 명시해도 발생 날짜를 추정해 쓰지 않는다.
- 생성에는 본인 기여로 확인한 수행 이력과 확정 성과만 주장 근거로 사용한다. 나머지는 보완 질문으로 구분한다.
- 문장별 근거 ID, 입력 자료의 버전/스냅샷, 생성 모델·프롬프트 버전·생성 시각·사용자 수정 버전을 남긴다.
- **수용:** 원본 변경 후에도 당시 어떤 자료로 생성했는지 추적 가능하다. 같은 문장이 다시 생성된다는 보장이 아니라 입력·변경 이력의 재현을 보장한다.
- **수용:** 본인 기여 없는 팀 성과, 미확정 수치, 선택 기간 밖 자료는 사실 문장으로 포함되지 않는다. 근거가 없는 문장은 경고하거나 생성에서 제외한다. AI 실패에도 기록 조회·수정·기존 결과 내보내기는 가능하다.
- **수용:** 저장한 이전 버전과 사용자 편집을 새 생성으로 덮어쓰지 않는다. 실제 저장 내용과 Markdown 출력이 일치한다.

### R08. 일상 사용 중심 화면 [P1]

- 대시보드는 프로젝트별 개발/운영 상태, 다음 업무, 실제 미해결 문제, 수집 실패·확인 대기 항목을 우선한다. 전체 평균 하나로 프로젝트 상태를 대표하지 않는다.
- 프로젝트 안에서 계획·업무/문제·활동 근거·완료 확인·성과를 연속적으로 처리한다. 목표·완료 검토·브랜치는 프로젝트 문맥의 하위 화면으로 둔다.
- 전체 메뉴는 대시보드·프로젝트·업무 이력·경력 자료를 기본으로 제안한다. 연동/운영 설정은 별도 설정에 두며, 리포트는 기간별 이력 출력으로 연결한다. 새 메뉴가 새 DB 데이터 사본을 만들지 않는다.
- 기존 URL은 상세 링크/리다이렉트로 보존한다. 전역 확인 대기 목록과 프로젝트 목록은 동일 항목의 다른 조회다.
- **수용:** 대시보드의 확인 대기 항목에서 원본 근거까지 두 번 이하의 명시적 선택으로 이동한다. 처리 후 양쪽 화면에서 일관되게 사라진다. 조회 실패와 빈 목록을 구분한다.
- **수용:** 320/390/768/1440px에서 문서 가로 넘침·텍스트 겹침이 없다. 키보드 조작·저장 실패 재시도·다중 탭 충돌 처리를 검증한다. 느린 이전 요청이 새 선택 화면을 덮어쓰지 않는다.

### R09. 수치·리포트 조회 계약

**R09a [P0]: 서버 산정·출처 계약과 오해를 만드는 표시 중단.**

- 서버 조회 결과에 기준 시각, 기간/시간대, 대상 프로젝트, 산식, 분모·분자, 제외 항목, 출처 범위를 포함한다.
- 기간은 사용자 시간대 기준 반개구간 `[시작, 종료 다음 날)`로 정의한다. 실제 완료 시각이 없는 과거 데이터는 완료 추이에 넣지 않는다.
- 계획 범위 변경 이력을 남긴다. 과거 계획 버전/상태 이력이 없는 날짜의 진척 곡선은 추정하지 않는다.
- **수용:** 프로젝트 상태·문서·로그 수에 임의 점수를 부여한 진척 후보가 API/화면/Markdown에서 제거된다. 모든 진척 표시는 공통 산식과 근거를 사용하거나 산정 불가로 표시한다. 200건 조회 상한은 전체 수집 건수와 구분한다.

**R09b [P1]: 기간별 리포트·출력과 조회 일관성.**

- 리포트는 승인 업무·실제 상태 전이·업무 로그·확인한 성과를 조회하며 문서 추출 항목만으로 잔여 업무를 대신 집계하지 않는다.
- **수용:** 같은 필터·같은 데이터 스냅샷에서는 화면과 리포트가 동일한 기록 집합을 사용한다. 새 데이터가 들어와 재생성되면 기준 버전을 갱신한다. 요청 조건 변경 후 생성 실패 시 이전 결과가 현재 결과인 것처럼 보이지 않는다.

### R10. 개인 서비스 운영·보존 [P0]

- 운영 데이터 수정 전 백업과 변경 대상 미리보기를 제공한다. 프로젝트는 기본적으로 보관 처리하며 영구 삭제에는 연결 자료 영향과 확인이 필요하다.
- 스키마 migration과 사업 데이터 재분류·정리는 분리한다. 배포가 임의로 사용자 계획·성과를 재작성하거나 샘플 정리를 실행하지 않는다.
- 검증한 commit SHA로 배포하고 실행 버전·migration 결과·readiness를 확인한다. 이전 앱 버전과 DB 변경의 복구 경계를 문서화한다.
- 인증된 UI/API, 서명 검증된 웹훅, 최소한의 공개 정적 자산 경계를 유지한다. 비밀값·비공개 원문을 로그/커밋/공개 출력에 노출하지 않는다.
- 외부 AI에는 선택된 최소 문맥만 전송한다. 비공개 저장소 자료의 외부 전송 여부를 사용자가 설정할 수 있고 키·토큰은 입력에서 제외한다. 외부 전송을 끄면 수동 기록·확인·출력이 계속 가능하다.
- **수용:** 미인증 접근·다른 owner 참조·잘못된 웹훅 서명은 거부된다. 백업을 격리 DB에 복원해 프로젝트·근거·성과 연결을 대조한다. 예약 백업 실패가 사용자에게 드러난다.
- **수용:** 배포 전후 세 프로젝트의 사용자 입력과 상태가 보존된다. 외부 API·AI 장애가 기록 CRUD를 막지 않는다. 재시작 후에도 수집 실패 내역과 재시도 상태가 남는다.
- 초기 운영 목표 제안은 일일 백업/RPO 24시간·복구 RTO 4시간이다. 아직 달성 사실이 아니며 실제 복원 리허설과 사용자 요구 확인 후 확정한다.

## 7. 데이터 구조와 전환 원칙

- 기존 프로젝트·WBS·업무 로그·성과·경력 자료를 재사용한다. 화면마다 동일 자료의 저장소를 만들지 않는다.
- 승인 상태, 개인 기여, 실제 완료 전이, 확인 기록, 계획 버전, 생성 근거 버전이 필요한 최소 확장이다. 정확한 DDL은 구현 단계에서 정한다.
- 원본 근거와 업무/성과 사이의 다대다 관계는 FK를 검증할 수 있는 관계로 표현한다. 기존 UUID 배열을 검증 없이 늘리거나 관계를 JSON으로 숨기지 않는다.
- 외부 상태의 동기화와 로컬 업무 상태 변경 권한을 분리한다. 이벤트 수신 기록과 사용자 판단 이력을 같은 row의 updated_at 하나로 대체하지 않는다.
- 과거 migration은 수정하지 않는다. 새 migration으로 구조를 추가하고, 데이터 전환은 dry-run 결과와 백업을 확인한 별도 작업으로 수행한다.
- 기존 auto/keyword 자료는 원본과 분류 이력을 보존한 채 참고/확인 대기로 전환한다. 이미 사용자 편집·확인한 항목은 우선 보호하고, 이력을 판별할 수 없으면 자동 삭제·재확정하지 않는다.
- 사용자 편집은 명시적 편집/확인 이력 또는 당시 자동 생성 원본과의 비교로 판별한다. 현재 생성 규칙이나 updated_at만으로 무편집을 추정하지 않는다. 비교 근거가 없으면 `편집 여부 미확인`으로 보호한다.
- dry-run에는 프로젝트별 대상 ID·기존 값·제안 값·판정 근거·연결 관계·편집 판별 결과·유지/전환/검토 대기 건수를 출력한다. 민감한 원문은 공개 로그에 남기지 않는다.
- **전환 수용:** 대상 ID마다 전후 대응이 존재하고 승인하지 않은 삭제가 0건이다. 보호 대상의 사용자 필드·확인 이력·연결 관계는 전후 동일하며 고아 참조가 0건이다. 재실행 시 추가 변경이 없고 격리 복원 결과가 변경 전 기준과 일치한다.
- 기존 경력 자료는 유지하되 입력 버전을 확인할 수 없으면 `이전 자료·근거 버전 미확인`으로 표시한다. 자동 재생성하거나 과거 확인 시각을 만들어 넣지 않는다.
